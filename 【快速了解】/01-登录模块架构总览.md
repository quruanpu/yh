# 登录模块架构总览（运小助 / yh-main）

> 目标：5 分钟看懂登录域全貌，不必通读源码。细节见同目录《02-账号与密码加载详解》《03-凭证存储恢复与风险清单》。

## 1. 系统定位

纯前端静态站（`index.html` + 按目录分包的原生 JS，无构建工具、无框架）。登录域在 `denglu/`，统一管理 **SCM / PMS / BI** 三套彼此独立系统的会话，核心思路：

- **一个弹窗状态机**（`LoginModule`）负责所有视图；
- **一套云端账户库**（Firebase RTDB `zhanghu/` 树）跨设备共享凭证；
- **一套设备指纹**（`device_XXXXXX`）绑定"哪台设备登录过哪些账号"；
- 业务模块一律通过 `LoginModule.requireCredentials(system)` 取凭证，不自己碰存储。

## 3. 脚本加载机制（重要）

`index.html` **只**静态引入 `denglu/app.js`，其余 10 个脚本由 `LoginModule.ensureDependencies()`（app.js:124-158）在运行时按固定顺序动态注入：

```
shebei/zhiwen → xinxi → huancun → app   （设备域，最先）
denglu/fir.js → yw/scm.js → yw/pms.js → yw/bi.js → auth/pzrz.js → auth/app.js
```

加载完成后校验 7 个全局模块是否齐全（`DeviceModule / FirebaseModule / ScmLoginModule / PmsLoginModule / BiLoginModule / LoginCredentialVerifier / LoginAuthModule`），缺任何一个抛错并降级为手动登录表单。每个脚本末尾 `window.XxxModule = Xxx` 挂载，全部是单例对象，无模块系统。

## 4. 启动链路

```
DOMContentLoaded
  └─ LoginModule.init()                       (app.js:249-259)
       ├─ createLoginDialog()                 预建弹窗 DOM
       ├─ ensureDeviceModule() → DeviceModule.ready() → AppFramework.initDeviceCode()
       └─ ensureDependencies()
            └─ checkAndForceLogin()           (app.js:262-302)
                 ├─ 强制弹窗（mandatory，不可关闭）显示"检测中"
                 ├─ _ensureBiProxy()           BI 代理探活，不阻塞主流程
                 ├─ recoverSystems(['scm','pms']) 与 10s 超时竞速
                 ├─ SCM 恢复成功 → showLoginSuccess('SCM')
                 │     └─ 并行 _autoLoginPms() / _autoLoginBi()（只补未恢复的）
                 ├─ 失败 → _showLoginForm() → SCM 表单 + autoFillScmAccount()
                 └─ finally → dispatchLoginReady（全生命周期只派发一次）
```

## 5. 三系统登录方式对比

| | SCM | PMS | BI |
|---|---|---|---|
| 凭证入口 | **账号+密码+图形验证码**（唯一有账密的系统） | 企微扫码 | 企微扫码 |
| 中转通道 | 腾讯云函数（scm.js:5-6，业务 API + OCR 两个地址） | 腾讯云函数（pms.js:5） | **自建固定代理**（`YejiGongju`，代理不通直接拒绝登录） |
| 流程 | `/captcha` → OCR 识别(10s 超时) → `/login/step1` → `/qrcode/init` → 1s 轮询 → `/login/step2` → `/credentials/full` | `get_qrcode` → `check_status` → `login` 一步换全量凭证 | 代理抓企微 `qrConnect` HTML 提取 key → JSONP 轮询 → OAuth 回调 → 代理从 Set-Cookie 捕获 token（两段回退）→ JWT 解码 exp |
| 产物 | credentials(token/cookies/provider_id…) + provider_info | credentials + user + permissions | token + tokenSig + exp + userInfo |
| 失效验证 | 真实接口试查 pageSize=1（pzrz.js:185-221） | 试查；**无 token 的凭证直接判有效**（pzrz.js:229-233） | 本地 JWT exp + 代理 `/api/validate-token`（pzrz.js:278-320） |
| 供应商归属 | 登录即有 provider_id/provider_name | permissions.sub_providers 多路取值归一 | 登录后调 BI 页面公司 selector：单公司取其 value，多公司固定 `jituan/多子公司`（app.js:490-527） |

## 6. 对外事件（document 级 CustomEvent）

| 事件 | 触发点 | detail 要点 |
|---|---|---|
| `loginReady` | checkAndForceLogin finally，仅一次 | `recoveredSystems`、`checkedAt` |
| `scmAuthenticated` | SCM 会话确立（恢复或登录），按 `providerId::username` 去重 | username、providerId、source、switched |
| `loginSuccess` | 任一系统登录/切换成功 | `{system:'SCM'|'PMS'|'BI', username, switched}` |
| `loginClosed` | 弹窗关闭 | selectedSystem |

外部模块监听 `loginSuccess` 时，`switched:true` 表示是账户切换，**不要重复写设备索引**。

## 7. 业务取凭证的标准姿势

```js
const res = await LoginModule.requireCredentials('scm'); // 'pms' | 'bi'
// res.ok === true → { source, credentials, local, provider, meta }
// res.ok === false → { code: 'NO_LOGIN'|'PROXY_UNAVAILABLE'|'TOKEN_EXPIRED'|... } 且已自动弹出登录窗
// 传 { silent: true } 则只返回结果不弹窗
```

内部即 `recoverSystems`（允许共享凭证）+ 10s 竞速（app.js:2131-2195）。BI 会先探活代理。

## 8. 关键外部依赖一览

- **腾讯云函数**（ap-guangzhou，前缀 `1317825751-`）：SCM 业务、SCM OCR、PMS 业务、SCM 商品查询校验接口（`gongn/chaxun/config.js:4-5`）。
- **BI 固定代理**：`YejiConfig.api.url`（zhiliao 域），探活 `GET /--api/status`，token 校验 `GET /api/validate-token`，会话粘性头 `X-BI-Proxy-Session`（`gongn/yunying/gongju.js:10-89`）。
- **Firebase RTDB**：`https://ai-moxing-default-rtdb.asia-southeast1.firebasedatabase.app`，配置硬编码在 `denglu/fir.js:4-13`（SDK 8.10.0 动态加载）。
- **企微**：SCM/PMS 走云函数中转的扫码协议（QRCODE_SCAN_* 状态机）；BI 走代理转发企微 SSO 页面。
