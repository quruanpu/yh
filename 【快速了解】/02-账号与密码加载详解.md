# 账号与密码加载详解（登录核心，重点阅读）

> 账号/密码**只存在于 SCM 体系**（PMS、BI 都是纯扫码，它们的"账号加载"就是凭证恢复）。
> 本文按"账号密码的一生"组织：字段定义 → 表单自动填充 → 登录后沉淀 → 启动自动恢复 → 账户列表切换。
> 行号基于 `denglu/` 当前源码。

## 0. 一图总览

```
                    ┌────────────────────────────────────────────────┐
                    │  Firebase RTDB  zhanghu/scm/...                 │
                    │  providers/{pid}/accounts/{acc}                 │
                    │    ├ credentials (token/cookies/provider_id)    │
                    │    ├ account_secret {account, password}  ←明文  │
                    │    ├ devices/{deviceId} (登录痕迹)               │
                    │    └ invalid 标记                               │
                    │  devices/{deviceId}/{pid_acc}  ←设备→账号索引    │
                    └────────────┬───────────────────▲───────────────┘
              读：自动填充/恢复/列表│                   │写：登录回写/共享/失效标记
                    ┌────────────▼───────────────────┴───────────────┐
                    │ localStorage  scm_login                         │
                    │  credentials + account_secret + provider_*      │
                    │  + credential_source(local/device/shared)       │
                    └────────────┬───────────────────────────────────┘
          ┌──────────────────────┼──────────────────────────┐
   ①表单自动填充          ②启动三级恢复                ③账户列表
   autoFillScmAccount    recoverSystems              renderAccountListView
   (预填输入框)           (免输入直接进系统)            (人工选择切换)
```

## 1. 字段与来源定义

- `account_secret = { account, password }`，**全链路明文**（localStorage、Firebase、共享对话框均不加密）。
- SCM 账户唯一键：`providerId::account`（`app.js:862-868`）。
- `credential_source` 三态：`local`（本机手输）/ `device`（云端设备索引恢复）/ `shared`（同供应商共享池）。`shared` 来源不可再共享（`canShareCurrentLogin`，app.js:677-684）。

## 2. 表单自动填充 autoFillScmAccount（app.js:1411-1463）

打开 SCM 登录表单（`renderScmFormView` 1336-1408）时自动执行，两条优先级：

**优先级 A — 共享账号预填**：从账户列表点了只有 `account_secret`、没有 credentials 的共享账号时，`validateAndSwitch`（app.js:1056-1058）把它存入 `state.prefillScmSecret`，此处直接填充返回。

**优先级 B — 云端设备索引自动加载**（常规路径）：

```
1. 禁用账号/密码/验证码输入框，placeholder = "自动加载中......"
2. FirebaseModule.getDeviceLogins('scm')            (fir.js:439-496)
   ├ 读 zhanghu/scm/devices/{当前设备码} 索引（本机登录过的账号）
   ├ 每条索引再精确拉取 providers/{pid}/accounts/{acc} 全量
   ├ 过滤：(有 credentials 或 account_secret) 且 !invalid
   └ 按 login_time 降序
3. 取最近一条 info，同时满足才填充：
   ├ info.account_secret 存在
   └ info.devices?.[当前设备码] 存在（双保险：确在本机登录过）
4. finally 恢复输入框；无记录/条件不满足 → 留空手动输入
```

边界：只尝试**最近一条**，不回退看更早账号；"当前设备登录过"是硬条件，换电脑不带出密码；验证码加载（`loadCaptcha` app.js:1466-1509）与账号加载并行，成功后验证码框预填占位 `******`。

**验证码 OCR**：点"下一步"（`verifyScmAccount` app.js:1512-1582）时值为 `******` → `recognizeCaptcha`（scm.js:83-110）POST OCR 云函数，10s 超时；失败降级手动输入。

## 3. 登录成功后的账号密码沉淀（app.js:2024-2055）

手动登录链路：`verifyScmAccount` → `ScmLoginModule.startLogin`（scm.js:197-240）→ 扫码轮询（app.js:1666-1704）→ `finalizeLogin`（scm.js:323-351）→ `showLoginSuccess('SCM')`：

```
1. 取 ScmLoginModule.getState() 的 account/credentials/providerInfo
2. 写 localStorage scm_login：
   account_secret: { account, password }        ←明文密码落盘 (app.js:2044)
   credential_source: 'local'，share_allowed: true
3. syncSharedCredentialAfterLogin('scm')        (app.js:471-487)
   └ 云端已有共享物(hasAny) → "缺什么补什么"回写 (app.js:796-819)
     云端什么都没有 → 不主动上传（密码只留本机）
```

设计意图：**密码默认不上云**；自动填充的 secret 永远来自"本机以前手输过"或"用户在凭证管理里主动共享过"。

## 4. 启动自动恢复 recoverSystems（auth/app.js:155-206）

免输入进入系统的主通道，每个系统按固定顺序三级尝试，命中即停：

```
第1级 tryLocal   localStorage {system}_login 有 credentials
                 → Verifier 真实接口验证 → 通过: applyLogin(写回会话+缓存)
                 → 失败: handleVerificationFailure
第2级 tryDevice  getDeviceLogins(system)（本机账号，倒序）→ 逐个验证，首个通过者胜出
第3级 trySharedProvider
                 先滚雪球定 provider_id：本地任一系统缓存 → 设备索引全系统扫 (auth/app.js:338-356)
                 → findAll*ByProviderId 共享池 → 逐个验证
```

**SCM 专属关键设计**（auth/app.js:13-35）：`clearLocal` 清失效凭证时**保留 `account_secret` 与 provider 信息**，只删 credentials。效果：token 过期 → 下次恢复失败 → 弹表单时 §2 自动填充仍带出账号密码 → 只需重新扫码。

**失败处置矩阵**（auth/app.js:251-262 + pzrz.js 七态分类）：

| 分类 | 典型原因 | canClearLocal | canMarkInvalid |
|---|---|---|---|
| invalid | 账号不存在/被禁用 | ✓ | ✓（云端标失效） |
| expired | 401/登录失效关键词 | ✓ | ✗ |
| temporary | 网络/5xx/业务错误 | ✗ | ✗ |
| permission_denied | 403/权限词 | ✗ | ✗ |
| missing/incomplete | 候选无凭证 | ✓ | ✗ |

`markAccountInvalid`（fir.js:328-356）同时写账户节点和**所有设备索引**的 `invalid=true`，防止死账号被反复尝试。

## 5. 账户列表与切换（app.js:915-1047, 1050-1085, 1126-1183）

"切换登录" → `renderAccountListView`：账号池 = 本地账号（`getVerifiedLocalAccount` 先真实验证，app.js:870-912）+ 云端共享池（`_source:'shared'`），去重键 `providerId::account`，渲染为 当前/失效/可登录 三态。

点"登录" → `validateAndSwitch` 分支：
- SCM 只有 account_secret → 预填账密走手动登录（§2 优先级 A 的来源）；
- 验证通过 → `switchToAccount`（**只切本地态，不写新设备索引**；source 判定：本地→local，共享但本设备在其 devices 中→device，否则 shared）；
- 明确失效 → 云端标失效 + 按钮置"失效" + 开登录表单；
- 网络类失败 → 按钮复位，不武断清除。

## 6. 设备码在账号加载中的三处作用

`DeviceModule`（shebei/app.js + zhiwen.js + huancun.js）：
- 指纹：约 30 项硬件信号（GPU/WebGL 参数、屏幕、音频采样率、Intl 等，zhiwen.js:77-122）→ `join('|')` → SHA-256 → **前 32 字节 XOR 折叠成 3 字节** → 6 位十六进制大写（zhiwen.js:124-138）→ `device_XXXXXX`；
- 缓存：localStorage `yxz_device_code_v1`，格式校验 `/^device_[A-F0-9]{6}$/`（huancun.js:13）；
- 用途：① Firebase 设备索引路径（决定"本机登录过的账号"）；② autoFill 的 `devices[deviceId]` 双保险校验；③ 切换账号时 `canShare` 判定。

注意：折叠后仅 24 bit（约 1677 万组合），约 4300 台设备即有 50% 碰撞概率（生日界），公司规模内风险低但存在。

## 7. PMS / BI 的"账号加载"

- **PMS**：无账密。恢复链同 §4；凭证含 token 时走 pmsUrl 试查，**无 token 直接判有效**（pzrz.js:229-233）。供应商从 `permissions.sub_providers / credentials / user_info` 多路归一（`_normalizePmsProvider` app.js:362-414）。
- **BI**：token + tokenSig + exp。验证先查本地 JWT exp，再走代理 `/api/validate-token`（pzrz.js:278-320）；注意验证过程会**临时覆写 `bi_login` 再在 finally 还原**，并发时有互相覆盖风险。登录后供应商由 BI 页面公司 selector 决定：单公司取其 value，多公司固定 `jituan/多子公司`（app.js:490-527）。
