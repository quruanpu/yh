## 二、目标架构

```
sjk/                          ← 数据中控（全站唯一数据库入口）
├── app.js                    # SjkModule：CloudBase 驱动 + 通用文档API + watch + 统一10秒超时 + 错误归一
└── README.md                 # 接口速查

数据库优化/                    ← 本文件夹（过程记录，不参与运行）
```

**分层原则**：
- `SjkModule` 只做**驱动级**通用能力（集合/文档 CRUD、watch、超时、匿名登录），**不含任何业务知识**；
- 业务逻辑（provider 归一、设备索引、账户结构等）留在各业务域自己的模块中（如登录域 `denglu/zhanghu.js`）；
- 将来换数据库 = 只改 `sjk/app.js` 驱动层，业务域零改动。

## 三、数据集合映射表（RTDB 路径 → CloudBase 集合）

| 原 RTDB 路径 | 集合 | 文档 ID | 说明 |
|---|---|---|---|
| `zhanghu/{sys}/providers/{pid}/accounts/{acc}` | `login_accounts` | `{sys}::{pidKey}::{accKey}` | 账户凭证全量（含 devices 内嵌 map、invalid 标记） |
| `zhanghu/{sys}/devices/{dev}/{idxKey}` | `device_logins` | `{sys}::{devKey}::{idxKey}` | 设备→账号索引 |
| `moban/yeji/{pid}/{key}` | `yeji_templates` | `{pidKey}::{key}` | BI 模板（每模板一文档，pid 字段用于查询） |
| `moban/yeji_mubiao/{pid}/ultra_v2` | `yeji_targets` | `{pidKey}` | 批量查询目标（ranges 内嵌，与原结构同构） |
| `yhq_gx/{pid}/{couponId}` | `coupons` | `{pidKey}::{couponId}` | 券（tasks 内嵌 map，与原结构同构） |
| `yhq_gx_index/{pid}` | `coupon_index` | `{pidKey}` | 券索引 |
| `jishiben/{pid}/...` | `notebooks` | `{pidKey}` | 记事本整树内嵌（`__meta.updated_at` 对应原路径） |
| `gongju_zx/items/{id}` | `gongju_items` | `{id}` | 工具中心 |
| `zhiliao/model_configs/{id}` | `model_configs` | `{configId}` | 模型配置仓库 |

- `{pidKey}/{accKey}` 沿用原 `_normalizeKey`（`.#$[]{}` → `_`），保证文档 ID 合法且与旧键可对照。
- 除文档 ID 外，**字段名与嵌套结构全部保持旧样**（`credentials/account_secret/provider_info/invalid/login_time/devices/tasks/ranges...`），这是"功能逻辑不变"的根基。

## 四、魔方式改造方法（如何保证功能逻辑不变）

1. **先固化契约再动手**：每个域改造前，在《02-数据契约》核对该域的读/写/监听清单与字段结构——旧代码是唯一事实源；
2. **签名对齐**：新模块方法保持旧方法的**参数与返回结构一致**（如 `getDeviceLogins(system)` 仍返回 `{scm:[],pms:[],bi:[]}` 且每项字段相同），调用方只换对象名与必要的调用行；
3. **一次只拼一面**：按域推进（登录域 → BI 域 → 优惠券域 → 杂项域），每域完成即更新《01-进度状态》并 git 提交，出问题精确回滚到上一个"拼好的面"；
4. **不变量清单**（全程不得变化）：localStorage 键与结构、`loginSuccess/loginReady/scmAuthenticated` 等事件、验证分类器（pzrz.js）、业务判定逻辑（如自动填充的双保险条件）；
5. **每文件改造必先重读源码**再编辑，防止记忆漂移；改完 `read_lints` 校验。

## 五、已知风险与对策

| 风险 | 对策 |
|---|---|
| 原 `saveSystemLogin` 是 RTDB 多路径原子写（账户+索引一次提交） | CloudBase 改为两文档顺序写；中间失败概率极低，失败即告警日志，下次登录会自动补齐（账户与索引均可重建） |
| `notebooks` 整树内嵌单文档，笔记多可能逼近文档大小上限 | 记录于此；超限时再拆文档（属后续优化，不影响本期行为对齐） |
| `watch()` 长连接资源点消耗 | 优惠券实时监听仅一个连接；体验版额度内观察，超限再议降级轮询 |
| 体验版资源点 3000/月 | 观察用量看板，不够升个人版（¥19.9/月，环境与数据保留） |
| Google 申诉成功后旧数据导出 | 届时用 RTDB REST 全量 dump + 导入脚本（见《02-数据契约》迁移节） |
