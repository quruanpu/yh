# 06 · 实时推送设计（方案 C：写时广播 + 即时拉取 + 兜底轮询）

> 前提：8 人团队、按需使用、页面长线挂着；日请求几百~几千；可能有"几千个 8 位编码（字母+数字）"的批量存储与几万次读取。
> 硬约束：功能/布局/样式完全不变；数据库层保持统一（全部收口在 sjk/ + Worker），后续换库只改数据库层。

## 1. 配额核算（Workers Free + D1 Free + DO Free）

### 免费额度（官方定价页口径）
| 计费项 | 免费限额 | 说明 |
|---|---|---|
| Worker/DO 请求 | 100,000 次/天 | 所有 Worker 脚本合计 |
| D1 行写 | 100,000 行/天 | 2026-09 起超限硬拒 |
| D1 行读 | 5,000,000 行/天 | **按扫描行数计**（无索引查询=全表行数） |
| D1/DO 存储 | 5 GB | |
| DO duration | ~13,000 GB-s/天 | WebSocket Hibernation 休眠连接不计时长 |
| DO 对象数 | ~1000 个（免费层） | 我们只用 1 个全局实例 |

### 8 人团队用量建模（偏保守：取较重的使用假设）

**请求（Workers+DO 合计 10 万/天）**：
| 项 | 估算 |
|---|---|
| 普通读写（日常业务） | 1,000~5,000 |
| 编码批量写入 | 5,000（假设一天存 5 千码） |
| 读取请求 | 5,000~20,000 |
| 写路径通知（Worker→DO 内部调用） | ≈写入数（5,000） |
| 兜底轮询（8 人 × 8h × 2 监听 × 每 60s） | ≈ 11,500 |
| **合计** | **≈ 1.7~4.3 万/天 → 占限额 17%~43%** ✅ |

**D1 行写（10 万/天）**：
- 逐码一文档：5,000 行写/天 ✅（5%）
- 批次内嵌（推荐）：≤100 行写/天 ✅（几乎为零）

**D1 行读（500 万/天）——这是唯一需要认真设计的项**：
| 读取形态 | 每次查询行读 | 日行读（假设 2 万次读请求/天） | 判定 |
|---|---|---|---|
| ❌ 逐码一文档（5 万行集合）+ 无索引查询 | ≈ 50,000（全扫） | 10 亿+ → **爆表 200 倍** | 禁止 |
| ✅ **批次内嵌**（一批一文档，几千码在 data JSON 内） | ≈ 1~批次文档数 | **≤ 5 万/天 → 1%** | **推荐** |
| ✅ 大集合 + 表达式索引 | ≈ 匹配行数 | 低 | 备选 |

**存储（"占多少内存"的直接回答）**：
- 几万个 8 位码：每码 JSON 开销约 20~30 字节 → 5 万码 ≈ **1.5~5 MB**
- D1/DO 免费存储 5 GB → **占比 0.1%**，存储完全无压力；
- 服务端**无常驻内存数据**（D1 落盘、DO 仅活跃连接的轻量状态，休眠时几乎为零）。

**结论：方案 C 在 8 人场景下免费额度完全够用**——前提是遵守一条设计纪律：**大批量编码必须"批次内嵌"存储（一批一文档），禁止逐码一文档**（详见 §4）。

## 2. 架构（写时广播 + 即时拉取 + 兜底轮询）

```
任何人写数据
  → Worker 写 D1（权威数据）
  → Worker 顺带内部调用 YhNotifyDO /notify {collection}   （写路径 +1 内部调用）
  → DO 通过 WebSocket 广播 {collection} 给所有订阅页面（Hibernation，毫秒级）

其他页面（启动时建立 1 条 WebSocket 长连接）
  → 收到 {collection} 通知 → 立即 getWhere/getAll 拉权威数据 → 现有回调（UI 更新）
  → 60s 兜底轮询持续（防通知丢失）
  → WS 断线：指数退避重连；期间退化为 60s 轮询（数据最终一致）
```

- 延迟：**写入 → 其他端可见 <1 秒**；
- DO 单实例（idFromName('global')）够用（内部 8 人）；
- **通知-拉取混合**是 Slack/Discord/GitHub 同款主流模式：推送只传"变化信号"，数据一律拉权威副本——通知丢失不影响正确性（轮询兜底）。

## 3. DO 设计（加入现有 Worker，单文件同部署）

```
export class YhNotifyDO {
  fetch(request) {
    /connect?token=...&collections=a,b  → WebSocket 升级（校验令牌/Origin）→ state.acceptWebSocket(ws, [tags])
    /notify { collection }              → 遍历 state.getWebSockets(collection tag) 发送 {collection}
  }
  webSocketMessage(ws, msg) { /* 可选：心跳/订阅变更 */ }
  webSocketClose(ws) { /* hibernation 自动清理 */ }
}
```
- Hibernation：页面挂机时连接休眠（不耗 duration），广播时按需唤醒发送；
- Worker 写路径通知：`env.YH_NOTIFY.idFromName('global')` → `stub.fetch('/notify')`（内部调用，失败 try/catch 忽略——不阻断写入）；
- wrangler.toml 增加 durable_objects 绑定与 migrations（new_sqlite_classes）。

## 4. 前端订阅层改造（sjk/app.js 内部，API 不变）

- `watchWhere/watchCollection` 重写：
  1. WebSocket 连 `config.wsUrl`（生产 `wss://ly.cqytyy.top/api/sjk-ws`——**同源 WS**，Vercel 代理支持 WebSocket 转发；本地 `ws://localhost:8787`）
  2. 连接后发送订阅清单（collections + token 首消息认证）
  3. 收到 `{collection}` 通知 → 调对应 fetcher 拉取 → 回调 `{ docs, type:'push' }`
  4. **60s 兜底轮询并行保留**
  5. 断线：指数退避重连（1s→2s→4s…上限 60s）；重连成功立即补拉一次
- 回调签名 `{ docs, type }` 不变（type: 'push'|'poll'）→ **业务域零改动**；
- `config.wsUrl` 支持 localStorage 覆盖（本地联调开关，与 gatewayUrl 同机制）。

## 5. 降级链（可靠性设计）

```
WS 正常：推送即时（<1s）
WS 断：自动退回 60s 轮询（数据最终一致）+ 后台重连
DO 异常：同上（轮询独立于 DO 工作）
全挂（CF 不可达）：前端 10s 超时报错（现有保护）
```
任何一层失效都不会比"现状 10s 轮询"更差。

## 6. 大批量编码的存储形态（关键设计约束）

| 形态 | 结构 | 行写/天 | 行读/天 | 判定 |
|---|---|---|---|---|
| ❌ 逐码一文档 | 每码 1 行（5 万行） | 5,000 | 全扫 → 数百万 | **禁止**（行读爆表） |
| ✅ 批次内嵌 | 一批 1 文档 `data.codes = ['AB12CD34',...]`（几千码/文档） | ≤100 | 每次读 1 行 | **采用** |
| ✅ 备选：高频字段表达式索引 | `CREATE INDEX ... ON docs(json_extract(data,'$.provider_id'))` | — | 走索引 | 大集合查询优化备用 |

- 领码/消费码的原子性：单条 `UPDATE ... SET data=json_set(...)` 条件更新（复用 updateWhere 机制）；
- 单文档大小：5 千码 ≈ 50KB（无实际压力；超大批次按 5 千/文档分批）。
