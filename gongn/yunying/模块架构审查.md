# BI 模块架构审查

## 模块定位

`gongn/yunying` 是优惠券前端系统里的 BI 运营查询大模块。它通过 `AppFramework.register` 注册，通过 `AppFramework.setModuleInstance('yunying', this)` 暴露模块实例。

当前模块不是 ES module 形态，而是现有系统风格下的全局对象 + mixin 架构。企业级优化原则是在不改变 UI 和运行方式的前提下，逐步收紧边界、减少重复、把业务服务从 UI 里拆出来。

## 外部依赖

BI 模块依赖这些系统能力：

- `AppFramework`：模块注册、模块实例托管。
- `LoginModule`：BI 登录凭证、登录弹窗、登录态恢复。
- `FirebaseModule`：VPN 节点、模板、目标数据持久化。
- `ZhiLiaoModule`：模型网关、AI 配置、模型协议和 fallback。
- `Tongzhi`：通知、确认弹窗。
- `XLSX`：目标模板和导出文件处理。
- `html2canvas`：弹窗复制图片能力，按需动态加载。

约束：BI 模块应只依赖这些稳定系统入口，不应反向要求其它业务模块了解 BI 内部状态。

## 当前内部结构

主入口：

- `app.js`：模块注册、状态、页面渲染、mixin 组合、AI 动态加载。
- `config.js`：BI Ultra 配置。
- `gongju.js`：代理、请求、VPN 节点等工具。

主查询：

- `zx/sx.js`：筛选器。
- `zx/cx.js`：连接、登录态、请求构造、主查询。
- `zx/cx/fw/gz.js`：主查询动态参数规则和白名单校验。
- `zx/cx/fw/yw.js`：主查询业务壳服务，供 UI 默认查询和 AI 动态查询共用。
- `zx/jg.js`：主查询结果渲染。
- `zx/mb.js`：模板。
- `zx/pz/*`：字段配置。

BI 查询面板：

- `zx/plcx.js`：BI 查询面板 UI、刷新、下载、表格渲染。
- `zx/plcx/fw/gz.js`：动态查询参数规则。
- `zx/plcx/fw/plcx.js`：BI 查询面板业务服务。
- `zx/plcx/fw/qs.js`：指标详解动态查询业务服务。
- `zx/plcx/fw/yw.js`：服务聚合导出，保持 `app.js` mixin 稳定。
- `zx/plcx/mb/*`：目标。
- `zx/plcx/hb/*`：合并模板。
- `zx/plcx/jh/*`：查询计划。

指标详解：

- `zx/plcx/qs/yw.js`：指标详解 UI 和默认打开链路。
- `zx/plcx/qs/gz.js`：基础规则。
- `zx/plcx/qs/zfx/*`：值模型。
- `zx/plcx/qs/lfx/*`：率模型。
- `zx/plcx/qs/sf/*`：算法辅助。

AI：

- `zx/ai/app.js`：BI AI 公共调用层，继承智聊模型能力。
- `zx/ai/gz.js`：AI 公共规则、响应解析、工具消息。
- `zx/ai/yw.js`：AI 输入、状态、流式读取辅助。
- `zx/ai/ty/*`：统一 BI AI 助手 UI、上下文聚合、工具路由。
- `zx/ai/main/gj/*`：主查询工具。
- `zx/plcx/ai/gj/*`：BI 查询面板工具。
- `zx/plcx/qs/ai/gj/*`：指标详解工具。

## 依赖方向

推荐方向：

1. UI 调用业务服务。
2. AI 工具调用业务服务。
3. 业务服务复用查询计划、目标、合并和算法。
4. 业务服务不直接渲染 UI。
5. AI 不直接计算业务指标。

当前已完成：

- BI 查询面板 UI 和 AI 共用 `runBatchQueryService`。
- 主查询 UI 和 AI 共用 `runMainQueryService`；UI 以 `inheritCurrent:true` 沿用当前页面状态，AI 默认使用纯净默认口径，也可显式继承当前页面。
- 指标详解 AI 使用 `runTrendQueryService`，不再依赖弹窗序号。
- BI 查询服务和指标详解服务已拆分为 `fw/plcx.js`、`fw/qs.js`。
- AI 多工具并发复用 `YejiAiApp.runConcurrentQueries`。
- 统一 AI 工具循环增加最大轮次保护。
- `YejiModule.state.domains` 已建立 live facade，按 `connection/main/filters/templates/fields/batch/trend/ai/ui` 分域，但保留全部扁平字段兼容。
- 样式注入脚本和 AI 动态加载已改为脚本清单化，不改变加载顺序。
- 统一 BI AI 面板业务已通过 `getBiAiState()` 访问 `domains.ai`，根 `biAi*` 字段仍作为事实源兼容。
- 三个 AI 私有工具入口已通过 `YejiAiApp.createToolApp` 生成，保留各自工具名、参数解析和全局导出。
- `app.js` 已提供 `getStateDomain()`、`getConnectionState()`，入口层连接状态读写开始通过状态域 facade 收口。
- `checkBiModuleReady()` 已作为 BI 启动诊断入口，用于发现核心全局依赖缺失，不改变 UI 和业务流程。

## 仍需注意的边界

- `YejiModule.state` 仍是主查询、BI 查询、指标详解、AI 共用状态仓库。`state.domains` 是过渡层，不应删除扁平字段。
- `fw/qs.js` 仍复用 `qs/yw.js` 的提取和计算函数，这是合理复用，但后续可继续把纯计算下沉到规则层。
- `zx/cx/fw/yw.js` 是主查询业务壳，`zx/cx.js` 仍保留连接、登录态、请求体构造和 UI 查询状态控制；这是当前全局 mixin 架构下的低风险拆分边界。
- `app.js` 静态 mixin 依赖全局加载顺序。短期通过 `index.html` 顺序保证，长期可规划模块加载清单化。
- 多个 AI prompt 仍有相似基础规则，后续可抽公共片段，减少漂移。

## 优化分级

低风险：

- 保持 `fw/plcx.js`、`fw/qs.js` 拆分。
- 把 AI 工具并发、工具消息、参数解析放入 `zx/ai/app.js`。
- 使用 `YejiAiApp.createToolApp` 创建私有工具入口，减少薄分发器重复。
- 清理旧 AI 文档和无用函数。
- 保持动态加载清单化，并在下一阶段评估静态 BI 主链迁移。
- 入口层连接状态读写通过 `getConnectionState()` 收口，保留查询链路原有判断逻辑。
- 建立 BI 模块启动依赖诊断 `checkBiModuleReady()`。

中风险：

- 抽公共 prompt 片段。
- 把 `fw/qs.js` 中趋势序列查询和 UI 默认趋势查询进一步共用同一服务。
- 将 `zx/cx.js`、`zx/plcx.js`、`zx/jg.js`、`zx/pz/zd.js` 中的连接状态判断逐步迁移到 `getConnectionState()`。

高风险：

- 将各子模块读写从扁平 `state.xxx` 逐步迁移到 `state.domains.*.xxx`。
- 改为 ES module 或完整依赖注入。
- 重构 `YejiGongju` 与登录、Firebase、VPN 节点监听的握手。

## 当前结论

当前结构已经满足现有系统风格下的模块化要求：BI 大模块独立注册，主查询、BI 查询面板、指标详解、AI 调用层分别有清晰目录和服务入口。

下一阶段若继续企业级演进，应优先做状态域隔离和加载清单化，而不是继续无边界拆文件。
